1.1

Introduction to Database Management Systems

Data, information, database, DBMS

Data
Raw, unprocessed facts with no context by themselves. Example: 25, Pune, B.Tech.
Information
Data that has been processed and given meaning. Example: "Rohan, age 25, studies B.Tech in Pune".
Database
An organised, persistent collection of logically related data, stored so that it can be retrieved, updated and managed easily. A college database holds students, courses, faculty and results together.
DBMS (Database Management System)
Software that lets users and programs define, create, store, retrieve, update and control a database. It sits between the users and the stored data. Examples: Oracle, MySQL, PostgreSQL, SQL Server (relational), MongoDB (NoSQL).
Database system
Database + DBMS + application programs + users. This is what people usually mean in practice.

Main characteristics of a DBMS

  • Self-describing: the database stores its own structure (tables, columns, types) in a catalog or data dictionary.
  • Data abstraction: users work with a simple view and never see how bytes sit on disk (see 1.4).
  • Multiple views: a student sees marks, the accounts office sees fees, from the same data.
  • Sharing and concurrency: many users can read and write at the same time without corrupting data.
  • Controlled redundancy and integrity: duplicates are minimised and rules (constraints) keep data valid.
  • Security: access is limited by user and by privilege.
  • Backup and recovery: data survives crashes and power failures.

Components of a database system

1.2

Purpose of Database Systems

Before DBMSs, organisations kept data in separate files, each handled by its own program. A university would have one file for admissions, another for exams, another for the library. This file-processing approach caused eight classic problems. Each problem is the reason a DBMS exists.

#Problem in file systemsExampleHow a DBMS solves it
1Data redundancy and inconsistencyA student's address is stored in admission, library and hostel files. After a move, only one file is updated.One central copy; normalisation
2Difficulty in accessing data"List students with CGPA above 8 in Pune" needs a new program to be written.Query language (SQL) for ad-hoc queries
3Data isolationData is scattered over files in different formats.One uniform model for all data
4Integrity problemsRule "balance must not be negative" is buried in program code, and changing it means editing many programs.Declared constraints (CHECK, PRIMARY KEY, FOREIGN KEY)
5Atomicity problemsTransfer of ₹1000 fails after debit but before credit.Transactions: all or nothing (rollback)
6Concurrent-access anomaliesTwo clerks update the same balance together; one update is lost.Locking and concurrency control
7Security problemsAn exam clerk can open payroll files.Authorisation, roles, privileges
8No data independenceChanging a record layout breaks every program.Three-level abstraction (see 1.4)

Advantages of a DBMS

  • Reduced redundancy and better consistency.
  • Data sharing among many users and applications.
  • Stronger integrity and security.
  • Backup, recovery and crash safety.
  • Faster development because programmers reuse a standard query language.
  • Data independence, so storage can change without rewriting programs.

Disadvantages

  • High cost of software, hardware and trained staff.
  • Complexity of design and administration.
  • Overhead for small, single-user applications where a spreadsheet is enough.
  • A single point of failure unless replication is used.

1.4

View of Data: Abstraction, Schemas and Independence

PYQ · Winter 2025 (IT) · 10 marks

A major purpose of a DBMS is to give users an abstract view of data. It hides how data is stored and maintained, and shows only what each user needs. This hiding is done in three levels, called the degrees of data abstraction.

The three levels

1. Physical level (internal level)
The lowest level. Describes how data is physically stored: files, disk blocks, record formats, indexes, compression. Only the DBMS, the OS and the DBA deal with it.
2. Logical level (conceptual level)
The middle level. Describes what data is stored and the relationships among data: tables, attributes, types, constraints. The DBA and developers work here. There is one logical schema for the whole database.
3. View level (external level)
The highest level. Describes only the part of the database a particular user group needs. There can be many views of one database, which also adds security (a student view hides salary data).
Example

Level by level for a STUDENT record:

  • View: a student portal shows name, CGPA and attendance only.
  • Logical: STUDENT(roll_no INT, name VARCHAR(40), dept VARCHAR(10), cgpa DECIMAL(3,2)).
  • Physical: records stored as fixed-length blocks in a heap file, with a B+ tree index on roll_no.

Instances and schemas

TermMeaningChanges how often?
SchemaThe overall design of the database (like a variable declaration or a blueprint).Rarely
InstanceThe data actually stored at a particular moment (like the value of a variable).Constantly

Schemas exist at each level: physical schema, logical schema and several subschemas (views).

Data independence

The ability to change the schema at one level without having to change the level above it.

TypeMeaningExample
Physical data independenceChange the physical schema without changing the logical schema or application programs.Add an index, move the file to an SSD, change the file organisation.
Logical data independenceChange the logical schema without changing views or application programs.Add a column email to STUDENT; existing views keep working.

Logical independence is harder to achieve than physical independence because applications depend heavily on the logical structure.

1.5

Database Languages

A DBMS offers different sub-languages for different jobs. In practice, SQL contains all of them. They are grouped by purpose:

LanguagePurposeMain commands
DDL Data Definition LanguageDefine and change the structure (schema). Output goes into the data dictionary.CREATE, ALTER, DROP, TRUNCATE, RENAME
DML Data Manipulation LanguageRetrieve and modify the data inside tables.SELECT, INSERT, UPDATE, DELETE
DCL Data Control LanguageControl access and privileges.GRANT, REVOKE
TCL Transaction Control LanguageManage transactions made by DML statements.COMMIT, ROLLBACK, SAVEPOINT

DDL example

CREATE TABLE student (
  roll_no  INT PRIMARY KEY,
  name     VARCHAR(40) NOT NULL,
  dept     VARCHAR(10),
  cgpa     DECIMAL(3,2) CHECK (cgpa BETWEEN 0 AND 10)
);
ALTER TABLE student ADD email VARCHAR(60);
DROP TABLE student;       -- removes structure and data
TRUNCATE TABLE student;   -- removes all rows, keeps structure

DML example and its two kinds

INSERT INTO student VALUES (101, 'Asha', 'IT', 8.7);
UPDATE student SET cgpa = 9.0 WHERE roll_no = 101;
DELETE FROM student WHERE roll_no = 101;
SELECT name, cgpa FROM student WHERE dept = 'IT';
  • Procedural DML: the user tells the system what data is needed and how to get it (relational algebra, PL/SQL loops).
  • Declarative (non-procedural) DML: the user says only what is needed; the optimiser decides how (SQL SELECT, relational calculus).

Some books put SELECT in its own group called DQL (Data Query Language). Either answer is accepted.

DCL and TCL example

GRANT SELECT, INSERT ON student TO clerk1;
REVOKE INSERT ON student FROM clerk1;

UPDATE account SET bal = bal - 1000 WHERE acc_no = 1;
SAVEPOINT after_debit;
UPDATE account SET bal = bal + 1000 WHERE acc_no = 2;
COMMIT;                         -- make permanent; ROLLBACK undoes

Note: in Oracle, DDL statements commit automatically, so they cannot be rolled back.

1.6

Database System Structure

PYQ · 10 marks

A database system is divided into modules, each handling one part of the work. The two main parts are the query processor and the storage manager, which sit above the disk storage.

Users and interfaces (top layer)

Naive users use application interfaces (forms). Application programmers write programs that call the DBMS. Sophisticated users type SQL or use query tools. The DBA uses administration tools.

Query processor

Turns user requests into low-level instructions the storage manager understands.

  • DDL interpreter: reads schema definitions and records them in the data dictionary.
  • DML compiler and query optimiser: translates a DML query into an evaluation plan of low-level operations, then picks the cheapest plan among many equivalent ones.
  • Query evaluation engine: executes the chosen plan and returns results.

Storage manager

The interface between the data on disk and the queries submitted. It is responsible for storing, retrieving and updating data.

  • Authorisation and integrity manager: checks that the user has the right privileges and that integrity constraints are satisfied.
  • Transaction manager: keeps the database consistent despite failures and schedules concurrent transactions so they do not conflict.
  • File manager: manages disk space and the data structures that represent information on disk.
  • Buffer manager: brings data from disk into main memory and decides what to keep there. It lets the database be larger than main memory.

Disk storage (data structures)

StructureContents
Data filesThe database itself
Data dictionary (catalog)Metadata: table names, columns, types, constraints, users and privileges
IndicesStructures such as B+ trees or hash tables for fast lookup
Statistical dataRow counts, value distributions; used by the optimiser

Application architecture

  • Two-tier: the client application talks directly to the database server (for example a desktop app using JDBC).
  • Three-tier: client (browser) → application server holding business logic → database server. Used by web applications; more secure and scalable.

Multi-user and distributed architectures are covered in Unit 5.

1.7

Data Models

PYQ · Summer 2026 · 10 marks

A data model is a collection of conceptual tools for describing data, data relationships, data semantics and constraints. It is the blueprint that tells us how data is organised and what can be done with it, like an architect's plan for a building.

Importance of data models

  • Bridge to reality: they turn a messy real-world situation into a clear structure that can be implemented.
  • Communication: designers, developers and clients share one picture of the requirements.
  • Consistency and integrity: constraints written into the model keep data valid.
  • Less redundancy: good modelling shows duplicated data early.
  • Cheaper changes: mistakes are cheap to fix on paper and expensive to fix after the database is built.
  • Basis for implementation: the DBMS, query language and storage structures are all derived from the model.

Basic building blocks of data models

Entity
A person, place, object, event or concept about which data is collected. Example: STUDENT, COURSE. In a relational table, an entity set becomes a table and one entity becomes a row.
Attribute
A property that describes an entity. Example: roll_no, name, cgpa. Becomes a column.
Relationship
An association between entities. Example: a STUDENT enrols in a COURSE. Described by its cardinality: one-to-one (1:1), one-to-many (1:N) and many-to-many (M:N).
Constraint
A rule that restricts the data to keep it valid. Example: cgpa must be between 0 and 10; every enrolment must refer to an existing student.

Some books add operations (insert, delete, update, retrieve) as a fifth building block, because a model also defines what can be done with the data.

Categories of data models

CategoryDescribesExamples
Conceptual (high-level)Concepts close to how users see dataER model, EER model
Representational (logical, implementation)Concepts users understand but also close to storageRelational, hierarchical, network, object-oriented
Physical (low-level)How data is stored on diskRecord formats, access paths, indexes

Evolution of data models

  1. 1950s–60sFile systems. Data in flat files processed by individual programs. Redundancy and inconsistency (see 1.2).
  2. 1960sHierarchical model. Data in a tree of parent and child records. IBM's IMS is the best-known system.
  3. late 1960sNetwork model. Graph of records with many-to-many links. Standardised by CODASYL.
  4. 1970Relational model. E. F. Codd proposed storing data in tables (relations) with a firm mathematical base. This led to System R, SQL, Oracle and today's RDBMSs.
  5. 1976Entity-Relationship model. Peter Chen's model for conceptual design, with diagrams.
  6. 1980s–90sObject-oriented and object-relational models. Store objects with attributes and methods, handle complex data such as images and CAD, and add object features to SQL.
  7. late 1990sSemi-structured models (XML). Self-describing, tagged data for exchange on the web. JSON later became the dominant form.
  8. 2000s–nowNoSQL and big-data models. Key-value, document, column-family and graph stores built for huge, distributed, flexible data (see Unit 6).

1.8

Entity-Relationship Model: Entities, Attributes, Relationships

Question bank

The ER model is a high-level conceptual model that describes the database as a set of entities, their attributes and the relationships among them, drawn as an ER diagram. It is used in the design phase, before any tables are created.

Entity and entity set

  • Entity: a distinguishable "thing" in the real world, such as the student Asha (roll 101).
  • Entity set: a collection of entities of the same type, such as all students. In diagrams, the rectangle stands for the entity set.
  • Strong entity: has a key of its own. Drawn as a single rectangle.
  • Weak entity: cannot be identified by its own attributes. It depends on an owner (strong) entity through an identifying relationship and has only a partial key (discriminator). Drawn as a double rectangle. Example: DEPENDENT of an EMPLOYEE, identified by (employee_id + dependent name).

1.10

Keys

Question bank

A key is an attribute, or set of attributes, that identifies tuples uniquely. Keys are what make relationships between tables possible.

Take STUDENT(roll_no, enrol_no, name, email, dept_id), where roll number, enrolment number and email are each unique, but names can repeat.

KeyDefinitionIn this example

Candidate keyA minimal super key: remove any attribute and uniqueness is lost.{roll_no}, {enrol_no}, {email}

Alternate keyCandidate keys not chosen as primary.enrol_no, email
Composite keyA key made of two or more attributes.ENROLMENT(roll_no, course_id): neither alone is unique
Foreign keyAn attribute that refers to the primary key of another (or the same) table. Enforces referential integrity.dept_id → DEPARTMENT(dept_id)

Surrogate keyAn artificial key with no business meaning, such as an auto-increment id.student_id SERIAL
CREATE TABLE department (dept_id INT PRIMARY KEY, dept_name VARCHAR(30));
CREATE TABLE student (
  roll_no  INT PRIMARY KEY,
  enrol_no VARCHAR(12) UNIQUE,
  email    VARCHAR(60) UNIQUE,
  name     VARCHAR(40),
  dept_id  INT REFERENCES department(dept_id)   -- foreign key
);

Relationship of the sets: primary key ⊂ candidate keys ⊂ super keys. Every candidate key is a super key, but not every super key is a candidate key.

Solved from question bank · Director / Play

DIRECTOR(DIRNUM, DIRNAME, DIRDOB) and PLAY(PLAYNO, PLAYNAME, DIRNUM).

  • Primary keys: DIRNUM in DIRECTOR, PLAYNO in PLAY.
  • Foreign key in PLAY: DIRNUM, referring to DIRECTOR(DIRNUM).
  • Candidate keys: DIRECTOR: DIRNUM. PLAY: PLAYNO. In the sample data DIRNAME and PLAYNAME are also unique, so they happen to qualify, but two directors or plays could share a name, so they are not reliable candidate keys. State this assumption.
  • ER model: DIRECTOR (1) —directs— (N) PLAY. Each play has one director (total on PLAY); a director may direct many plays.
Solved from question bank · Customer / BookOrders

CUSTOMER(CustID, CustName, AccntNo) and BOOKORDERS(OrderID, Title, CustID, Price).

  • Primary keys: CustID, OrderID.
  • Foreign key in BookOrders: CustID → CUSTOMER(CustID).
  • Candidate keys: CUSTOMER: CustID and AccntNo (an account number is unique per customer). BOOKORDERS: OrderID only.
  • ER model: CUSTOMER (1) —places— (N) BOOKORDERS.
  • Redundant data: in BOOKORDERS the same book title repeats with the same price ("The Dark Tower" 12.00, "Song of Susannah" 23.00). Title and price should move to a separate BOOK table, and BOOKORDERS should store only the book id. This removes the repetition and the risk of changing a price in one row only.
1.11

Database Design Process

Designing a database is a sequence of phases. Each phase produces something concrete that feeds the next.

  1. 1. Requirement analysisTalk to users, collect forms and reports, write down what data is needed and what operations are required.
  2. 2. Conceptual designDraw the ER (or EER) diagram: entities, attributes, relationships, constraints. Independent of any DBMS.
  3. 3. Logical designConvert the ER diagram into tables of the chosen model (relational), choose keys.
  4. 4. Schema refinementNormalise the tables to remove redundancy and anomalies.
  5. 5. Physical designChoose file organisation, indexes, partitioning and storage for performance.
  6. 6. Implementation and securityCreate the tables, load data, define views, privileges, backup plans, and test with real queries.
Example

Library system. Requirements: members borrow books, each book has authors and a publisher. Conceptual: MEMBER, BOOK, AUTHOR, PUBLISHER and borrows, written_by relationships. Logical: tables with primary and foreign keys. Refinement: split repeated publisher details into a PUBLISHER table. Physical: B+ tree index on book.title.

1.12

ER Diagram and Design Issues

Steps to draw an ER diagram

  1. Read the requirements and underline the nouns (candidate entities) and verbs (candidate relationships).
  2. List the attributes of each entity and pick a key.
  3. Mark weak entities and their owners.
  4. Identify relationships, then fix their cardinality and participation.
  5. Add attributes to relationships if needed (a M:N relationship often has them).
  6. State assumptions clearly, then draw neatly with labels.

Design issues

1. Entity or attribute?
Use an attribute when the thing has no properties of its own and is only a detail. Use an entity when it has its own attributes or takes part in relationships. Example: phone_number is an attribute. If we must store the phone's model, operator and plan, then PHONE should be an entity.
2. Entity or relationship?
An action that has its own data and is later referred to by other things often deserves an entity. Example: loan between CUSTOMER and BRANCH is better as a LOAN entity if it has amount, rate and payments.
3. Binary or n-ary relationships?
A ternary relationship can be replaced with several binary ones, but only when no information is lost. If "supplier supplies part to project" is only valid as a triple, keep it ternary.
4. Placement of attributes
Attributes of a 1:N relationship can be moved to the N side. Attributes of an M:N relationship must stay on the relationship (grade belongs to the enrolment, not to the student or the course).
5. Redundant attributes and relationships
Do not repeat information. Do not store dept_name in EMPLOYEE if EMPLOYEE already links to DEPARTMENT. Remove relationships that can be derived from others.
6. Weak entity or multivalued composite attribute?
A multivalued composite attribute such as dependent(name, age) can be modelled as a weak entity if you need to relate it further.
7. Choosing keys and avoiding surrogate confusion
Select stable, short keys. Names make poor keys.
1.13

Worked ER Design: Railway Reservation

Practice ER design

Question: Draw the ER diagram for a railway reservation database. List down the entities and relationships. Assume suitable data.

Step 1. Assumptions

  • A registered passenger books tickets. One ticket (identified by its PNR) belongs to one train, one journey date and one class.

Extended ER (EER) Features

PYQ · Summer 2026 + question bank

The Extended ER model adds object-oriented ideas to the basic ER model so that it can describe complex, hierarchical data more accurately. It is basic ER plus subclasses, superclasses, inheritance, specialization, generalization, categories and aggregation.

Specialization

A top-down process of dividing an entity set into more specific subclasses based on some distinguishing feature. EMPLOYEE can be specialised into FACULTY, STAFF and STUDENT_ASSISTANT. Each subclass keeps the attributes of the superclass and adds its own.

Generalization

The bottom-up reverse: several entity sets with common features are merged into a higher-level superclass. CAR and TRUCK, which both have registration_no and owner, are generalised into VEHICLE. The result looks the same as specialization; only the direction of thinking differs.

Attribute inheritance

A subclass inherits all attributes and relationships of its superclass. A FACULTY member automatically has ssn, name and salary and also has rank. If a subclass has two superclasses it uses multiple inheritance (a STUDENT_ASSISTANT is both an employee and a student).

Aggregation

The basic ER model cannot express a relationship between a relationship and an entity. Aggregation treats a relationship set (with the entities it links) as one higher-level entity so it can take part in another relationship.

Category (union type)

A subclass formed from the union of different superclasses. An OWNER of a vehicle may be a PERSON, a COMPANY or a BANK. OWNER is a category; an owner is exactly one of those, and inherits only from the one it belongs to.

2.1

Relational Model: Basic Concepts, Attributes and Domains

The relational model, proposed by E. F. Codd in 1970, represents the whole database as a collection of relations. A relation looks like a table of values, and every row says something about a real-world entity or relationship. It has a firm mathematical basis (set theory and predicate logic), which is why it replaced the hierarchical and network models.

Attributes and domains

Every attribute has a domain, and every value in a column must be atomic (a single indivisible value) and drawn from that domain. A domain is often written as a name plus a description: Phone_numbers: 10-digit numbers; Marks: integers 0 to 100. Two attributes may share a domain (billing_city and shipping_city) while meaning different things.

Properties of a relation

  • Each relation has a distinct name; each attribute name is unique within it.
  • Every cell holds one atomic value (no repeating groups).
  • The order of rows and the order of columns do not matter.
  • No two tuples are identical, because a relation is a set. A primary key enforces this.

Relational Integrity Constraints

PYQ · Summer 2026, Winter 2025 IT · 10 marks

Integrity constraints are rules that keep the data in a relational database correct and consistent. The DBMS checks them on every insert, update and delete, and rejects the operation if a rule would be broken.

1. Domain integrity

Every value of an attribute must belong to its domain: correct data type, length, range and format. Enforced with data types, NOT NULL, CHECK, DEFAULT.

CREATE TABLE student (
  roll_no INT PRIMARY KEY,
  age     INT CHECK (age BETWEEN 16 AND 60),
  gender  CHAR(1) CHECK (gender IN ('M','F','O')),
  city    VARCHAR(30) DEFAULT 'Pune'
);
-- INSERT ... age = 150  → rejected (outside domain)

2. Entity integrity

The primary key of every tuple must be unique and can never be NULL, because a tuple with no identity cannot be referred to. Enforced with PRIMARY KEY. Inserting a second student with roll_no = 101, or one with roll_no = NULL, is rejected.

3. Referential integrity

A foreign key value must either be NULL or match an existing primary key value in the referenced table. No tuple may refer to something that does not exist.

CREATE TABLE enrolment (
  roll_no INT,
  cid     INT,
  PRIMARY KEY (roll_no, cid),
  FOREIGN KEY (roll_no) REFERENCES student(roll_no) ON DELETE CASCADE,
  FOREIGN KEY (cid)     REFERENCES course(cid)     ON DELETE RESTRICT
);

4. Enterprise (general) constraints

Business rules that are specific to the organisation and go beyond keys and domains. They may involve several attributes or tables. Examples: "A faculty member cannot teach more than 4 courses per semester", "An account balance may not fall below the minimum balance", "Total marks cannot exceed 100". They are implemented with CHECK constraints, assertions or triggers (Unit 3).

5. Null constraints

NULL means "unknown, missing or not applicable". It is not zero and not blank. Comparison with NULL gives UNKNOWN, so SQL uses three-valued logic:

FALSEUNKNOWNFALSEUNKNOWN

Test with IS NULL or IS NOT NULL, never with = NULL. NOT NULL forbids nulls in a column. Primary-key columns can never be null.

6. Structural constraints

Rules about the shape of the data, which come from the model itself: each relation has a key, values are atomic, and relationships follow the cardinality and participation of the design.

PYQ · Winter 2025 (IT) · violating referential integrity

Question: inspect the impact of violating referential integrity, using a student-course enrolment database.

Take STUDENT(101 Asha, 102 Rohan), COURSE(C1 DBMS, C2 OS) and ENROLMENT(101,C1), (102,C2).

  • Insert violation: inserting enrolment (999, C1) when student 999 does not exist creates an orphan tuple. Reports would show an enrolment with no student.
  • Delete violation: deleting course C2 while (102, C2) remains leaves a dangling reference. A join of ENROLMENT with COURSE silently drops Rohan's enrolment, so totals are wrong.
  • Update violation: changing C1 to C9 in COURSE without updating ENROLMENT breaks every link to that course.

Impact: inconsistent and unreliable data, wrong query results and joins, lost or meaningless records (for example marks with no student), failures in applications that expect the parent row, and a loss of trust in the database.

Prevention: declare FOREIGN KEY with a delete rule (RESTRICT, CASCADE or SET NULL), so the DBMS refuses or repairs the change.

2.5

Features of Good Relational Design and Anomalies

Question bank

Converting an ER diagram gives a first set of tables. A good relational design must still be checked against these guidelines.

  • Clear meaning: each table represents one entity or one relationship, not a mixture of several.
  • Minimal redundancy: a fact is stored once.
  • No update anomalies: inserts, deletes and updates do not cause trouble.
  • Few NULLs: columns that are mostly null belong in a separate table.
  • No spurious tuples: splitting tables must not produce rows that were never there (see lossless joins in 2.11).

2.6

Functional Dependencies

A functional dependency (FD) X → Y says that if two tuples have the same value for X, they must have the same value for Y. We say "X determines Y". X is the determinant.

  • roll_no → name, dept (a roll number fixes the name and department).
  • dept_no → dept_name.
  • (roll_no, cid) → grade (a grade depends on both student and course).

An FD is a property of the meaning of the data, not of one particular instance. A sample table can only show that an FD does not hold, never prove that it does.

Kinds of functional dependency

KindMeaningExample
TrivialY ⊆ X; always true(roll_no, name) → name
Non-trivialY ⊄ Xroll_no → name
Full dependencyY depends on all of X, and on no proper subset of X(roll_no, cid) → grade
Partial dependencyY depends on part of a composite key(roll_no, cid) → student_name, because roll_no → student_name
Transitive dependencyX → Y and Y → Z, so X → Z through a non-key Yroll_no → dept_no → dept_name

Armstrong's axioms

Rules to derive new FDs from a given set F. They are sound (derive only true FDs) and complete (derive all of them).

RuleStatement
ReflexivityIf Y ⊆ X then X → Y
AugmentationIf X → Y then XZ → YZ
TransitivityIf X → Y and Y → Z then X → Z
Union (derived)If X → Y and X → Z then X → YZ
Decomposition (derived)If X → YZ then X → Y and X → Z
Pseudotransitivity (derived)If X → Y and WY → Z then WX → Z

Closure of an attribute set X⁺

X⁺ is the set of all attributes that X determines. Algorithm: start with result = X; repeat, for each FD A → B with A ⊆ result add B to result; stop when nothing changes.

Example

R(A, B, C, D, E) with F = { A → B, BC → D, D → E }. Find {A, C}⁺.

start            {A, C}
A → B            {A, B, C}
BC → D           {A, B, C, D}
D → E            {A, B, C, D, E}   all attributes

So AC determines every attribute, which means AC is a super key.

Finding candidate keys

  1. Attributes that never appear on the right side of any FD must be in every key. Here A and C.
  2. Compute the closure of that set. If it covers all attributes, it is a candidate key (and the only one, if no others can be built).
  3. If not, add other attributes one at a time and test again. Keep only minimal sets.

For the example, {A, C}⁺ is everything and neither A nor C alone is enough ({A}⁺ = {A,B}), so the only candidate key is AC.

Canonical (minimal) cover

A smallest equivalent set of FDs. Steps: (1) make every right side a single attribute; (2) remove extraneous attributes from left sides; (3) remove redundant FDs.

Example

F = { A → BC, B → C, A → B, AB → C }

1. Split right sides:   A→B, A→C, B→C, A→B, AB→C       (drop the duplicate A→B)
2. AB → C: A is extraneous because B → C already holds, so AB → C becomes B → C (duplicate)
3. A → C is redundant: A→B and B→C already give it
Canonical cover Fc = { A → B, B → C }
2.7

Atomic Domains and First Normal Form (1NF)

PYQ · question bank

Normalisation is the process of organising tables to remove redundancy and anomalies, moving through a sequence of normal forms, each stricter than the one before.

Atomic domains

A domain is atomic if its values are treated as indivisible units. A phone-number list "9876, 9123" in one cell is not atomic; a name stored as "Asha Rao" may or may not be, depending on whether the parts are used separately.

Definition of 1NF

A relation is in 1NF if every attribute contains only atomic (single) values: no multivalued attributes, no composite attributes in one cell and no repeating groups. Every row is identified by a primary key.

Example · converting to 1NF
roll_nonamephones
101Asha9876, 9123
102Rohan9555

Not in 1NF because phones holds a list. Two fixes:

Fix A. One row per value (primary key becomes (roll_no, phone)):

roll_nonamephone
101Asha9876
101Asha9123
102Rohan9555

Fix B. Separate table (preferred, no repeated names): STUDENT(roll_no, name) and STUDENT_PHONE(roll_no, phone).

Problems with 1NF

1NF removes lists, but the table can still hold a lot of redundancy. Consider ORDERS(order_id, product_id, product_name, qty, customer_name), key (order_id, product_id):

order_idproduct_idproduct_nameqtycustomer_name

  • Insertion anomaly: a new product cannot be recorded until someone orders it.
  • Deletion anomaly: deleting order O2 loses nothing here, but deleting the only order of a product loses the product name.
  • Update anomaly: renaming P1 means changing every row where P1 appears. The customer name repeats for each line of an order.

The cause is that some columns depend on only part of the key. Second normal form removes these.

2.8

Second Normal Form (2NF)

PYQ · question bank

A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on the whole candidate key. In other words, it has no partial dependency. A table whose key is a single attribute is automatically in 2NF.

Converting to 2NF

  1. Find the candidate key and list the FDs.
  2. Find attributes that depend on only part of the key.
  3. Move each such group into a new table whose key is that part of the key. Leave the rest in the original table.
Worked example

ORDERS(order_id, product_id, product_name, qty, customer_name). Key: (order_id, product_id).

order_id, product_id → qty
order_id             → customer_name      partial dependency
product_id           → product_name       partial dependency

Decompose:

ORDER_HEADER(order_id, customer_name)
PRODUCT(product_id, product_name)
ORDER_ITEM(order_id FK, product_id FK, qty)

Now each non-key column depends on the full key of its table. Product names and customer names are stored once.

2.9

Third Normal Form (3NF)

PYQ · question bank

A relation is in 3NF if it is in 2NF and has no transitive dependency: no non-prime attribute depends on another non-prime attribute.

Formal definition: for every non-trivial FD X → A, either X is a super key, or A is a prime attribute (part of some candidate key).

Worked example

STUDENT(roll_no, name, dept_id, dept_name, dept_head). Key: roll_no.

roll_no → name, dept_id
dept_id → dept_name, dept_head       dept_id is not a key
so roll_no → dept_id → dept_name     transitive dependency

Decompose:

STUDENT(roll_no, name, dept_id FK)
DEPARTMENT(dept_id, dept_name, dept_head)

A department's name and head are stored once, so they can be updated in one place, and a department can exist with no students.

Memory aid: every non-key attribute depends on the key (1NF), the whole key (2NF), and nothing but the key (3NF).

2.10

Boyce-Codd Normal Form (BCNF)

PYQ · Winter 2025 (E&TC) · 10 marks

A relation is in BCNF if for every non-trivial FD X → Y that holds in it, X is a super key. BCNF is a stricter, simpler version of 3NF. It removes the 3NF exception that allows a non-key determinant when the right side is a prime attribute.

Example · in 3NF but not in BCNF

TEACH(student, course, instructor). Rules: each instructor teaches only one course; a student has one instructor per course.

(student, course) → instructor
instructor        → course
studentcourseinstructor
AshaDBMSRao
RohanDBMSRao
AshaOSIyer

Candidate keys: {student, course} and {student, instructor}. In instructor → course the determinant is not a super key, so the table violates BCNF. It still satisfies 3NF because course is a prime attribute. Problem: the fact "Rao teaches DBMS" repeats in every row, and if Iyer's last student leaves, the fact that Iyer teaches OS disappears.

BCNF decomposition:

R1(instructor, course)             R2(student, instructor)

This is lossless (the common attribute instructor is a key of R1), but the original FD (student, course) → instructor can no longer be checked inside one table, so it is not dependency preserving.

2.11

Decomposition Using Functional Dependencies and Algorithms

PYQ · Winter 2025 (IT) · 10 marks

Decomposition replaces a relation R by two or more smaller relations whose attributes together cover R. A good decomposition has two properties.

1. Lossless-join decomposition

Joining the pieces back must give exactly the original relation, with no extra (spurious) tuples. Test for two relations: R is decomposed into R1 and R2 losslessly if and only if at least one of these holds in F⁺:

R1 ∩ R2  →  R1          or          R1 ∩ R2  →  R2

That is, the common attributes form a key of at least one piece.

A lossy decomposition shown with data

R(A, B, C) with F = {A → B}. Rows: (a1, b1, c1), (a2, b1, c2). Split into R1(A,B) and R2(B,C). The common attribute B is not a key of either piece.

R1 (A, B)R2 (B, C)R1 ⋈ R2
(a1, b1), (a2, b1)(b1, c1), (b1, c2)(a1,b1,c1) (a1,b1,c2) (a2,b1,c1) (a2,b1,c2)

The join yields 4 rows, two of which (bold) never existed. Information is lost because we can no longer tell the real rows from the fake ones. Splitting on A instead, R1(A,B) and R2(A,C), is lossless because A → AB.

2. Dependency preservation

Every FD of F should be enforceable by looking at a single decomposed table, without joining. Let Fi be the FDs of F⁺ whose attributes all lie in Ri. The decomposition is dependency preserving if (F1 ∪ F2 ∪ …)⁺ = F⁺.

Practical test (for each FD X → Y in F): set result = X; repeat until it stops growing: for each piece Ri, do result = result ∪ ((result ∩ Ri)⁺ ∩ Ri). If Y ⊆ result, the FD is preserved.

Worked answer · is this decomposition dependency preserving?

R(A, B, C), F = { A → B, B → C }. Candidate key: A. Compare two decompositions.

Algorithm 1: BCNF decomposition

result = { R }
while some Ri in result is not in BCNF:
    pick a violating FD  X → Y  in Ri   (X is not a super key of Ri)
    replace Ri by   Ri1 = (Ri − Y)   and   Ri2 = X ∪ Y

Always gives a lossless result in BCNF, but may lose dependencies. Applied to TEACH(student, course, instructor) with instructor → course: R1 = (instructor, course), R2 = (student, instructor).

Algorithm 2: 3NF synthesis

1. Compute a canonical cover Fc of F.
2. For each FD  X → Y  in Fc, create a relation  Ri = X ∪ Y.
3. If no Ri contains a candidate key of R, add one relation made of a candidate key.
4. Remove any relation that is contained in another.

Always gives a result in 3NF that is lossless and dependency preserving.

Example

R(A, B, C, D), F = { A → B, B → C }. Key: AD (A and D never appear on a right side; {A,D}⁺ = ABCD). Fc = F. Step 2 gives R1(A,B) and R2(B,C). Neither contains AD, so step 3 adds R3(A,D). Final: R1(A,B), R2(B,C), R3(A,D).

Modeling Temporal Data

An ordinary table shows only the current state: when a salary changes, the old value is overwritten and lost. Temporal data is data tied to time, and a temporal database keeps the history so that we can ask what was true at any past moment.

Kind of timeMeaningExample
Valid timeWhen a fact is true in the real world.Salary 48000 applied from 1 July 2023 to 31 Dec 2024.
Transaction timeWhen the fact was stored in the database. Set by the system and cannot be changed.That salary row was entered on 5 Aug 2023.
BitemporalBoth kinds together; lets you ask "what did we believe on date D about the situation on date E?"An audit of a backdated correction.
User-defined timeAn ordinary date column with no special meaning to the DBMS.date_of_birth

Design of a valid-time table

Add a start and an end column to each row, and include the start in the primary key, because the same employee has many rows.

CREATE TABLE emp_salary (
  eid         INT,
  salary      NUMBER(10,2),
  valid_from  DATE NOT NULL,
  valid_to    DATE DEFAULT DATE '9999-12-31',      -- open-ended = still true
  PRIMARY KEY (eid, valid_from),
  CHECK (valid_from <= valid_to)
);

-- salary on 15 March 2024 (point-in-time query)
SELECT salary FROM emp_salary
WHERE eid = 1 AND DATE '2024-03-15' BETWEEN valid_from AND valid_to;

-- raise from 1 Jan 2026: close the current row, then add the new one
UPDATE emp_salary SET valid_to = DATE '2025-12-31' WHERE eid = 1 AND valid_to = DATE '9999-12-31';
INSERT INTO emp_salary VALUES (1, 60000, DATE '2026-01-01', DATE '9999-12-31');

Issues to handle

  • No overlapping periods for the same employee. Enforce with a trigger or an exclusion constraint.
  • No gaps if the fact must always have a value.
  • Temporal primary key: the key is (entity id, start time), not the entity id alone.
  • Temporal referential integrity: a child row's period must lie within its parent's period. An employee cannot be assigned to a department before the department existed.
  • Temporal functional dependency: an FD such as eid → salary holds at each instant, not across all rows.
  • SQL:2011 adds PERIOD FOR and system-versioned tables (FOR SYSTEM_TIME AS OF), which maintain transaction time automatically.

SQL: Characteristics and Advantages

SQL (Structured Query Language) is the standard language for creating, querying and managing relational databases. It was developed at IBM in the 1970s (first called SEQUEL), became an ANSI standard in 1986 and an ISO standard in 1987, and is supported by Oracle, MySQL, PostgreSQL, SQL Server and others. The notes use Oracle syntax because the syllabus covers PL/SQL, and mention where other systems differ.

Characteristics

  • Declarative (non-procedural): you state what result you want, and the optimiser decides how to get it.
  • Set-oriented: one statement works on a whole set of rows at once.
  • One language for everything: definition, manipulation, control and transactions (DDL, DML, DCL, TCL).
  • English-like: SELECT name FROM student WHERE dept = 'IT' reads like a sentence.
  • Interactive and embeddable: used at a prompt or inside Java, C, Python and other programs.
  • Case-insensitive keywords: select and SELECT are the same. String values are case-sensitive in Oracle ('IT' differs from 'it').
  • Statements end with a semicolon (in most tools).

3.5

Views: Creating, Dropping, Updating Through Views

PYQ · Winter 2025 (E&TC) · short note

A view is a virtual table defined by a stored SELECT query. It holds no data of its own; each time it is used, the query runs against the base tables. It is the SQL form of the view level of abstraction (1.4).

CREATE VIEW it_staff AS
  SELECT emp_id, emp_name, salary
  FROM   employee
  WHERE  dept_id = 10;

SELECT * FROM it_staff WHERE salary > 50000;     -- used like a table
CREATE OR REPLACE VIEW it_staff AS ...;         -- change the definition
DROP VIEW it_staff;                             -- removes the view only, base data stays

Why use views

  • Security: expose only some columns or rows (a clerk's view hides salary).
  • Simplicity: hide complicated joins behind a simple name.
  • Logical data independence: if the base table changes, redefine the view and programs keep working.
  • Consistency: one shared definition of a calculation.

Updating through a view

A view is updatable (INSERT, UPDATE, DELETE pass through to the base table) only when each view row maps to exactly one base row. A view is normally not updatable if it contains:

  • DISTINCT, GROUP BY, HAVING or aggregate functions;
  • set operators (UNION etc.);
  • a join of several tables (limited updates only, on the key-preserved table);
  • columns that are expressions or leave out a NOT NULL column without a default (for inserts).
UPDATE it_staff SET salary = salary * 1.1 WHERE emp_id = 7;     -- changes employee table

CREATE VIEW it_staff2 AS
  SELECT * FROM employee WHERE dept_id = 10
  WITH CHECK OPTION;      -- rows inserted or updated must still satisfy dept_id = 10

WITH READ ONLY blocks all changes. A materialized view stores the query result physically and is refreshed periodically; it speeds up heavy reports but can be stale.

3.7

SELECT Query and Its Clauses

The SELECT statement retrieves data. Its general form:

SELECT   [DISTINCT] column list | expressions | *
FROM     table list (with joins)
WHERE    row condition
GROUP BY grouping columns
HAVING   group condition
ORDER BY sort columns [ASC | DESC];

Logical order of execution

  1. 1. FROMChoose tables and apply joins.
  2. 2. WHEREFilter individual rows.
  3. 3. GROUP BYForm groups of rows.
  4. 4. HAVINGFilter whole groups.
  5. 5. SELECTCompute the output columns, remove DISTINCT duplicates.
  6. 6. ORDER BYSort the final result.

This is why a column alias defined in SELECT can be used in ORDER BY but not in WHERE.

3.11

Nested Queries (Subqueries)

PYQ · Summer 2026 · 10 marks

A nested query (subquery, inner query) is a SELECT written inside another SQL statement, usually in brackets. The inner query runs first and its result is used by the outer query. A subquery can appear in WHERE, HAVING, FROM and SELECT, and inside INSERT, UPDATE and DELETE.

1. Single-row (scalar) subquery

Returns one value; used with =, >, <.

-- employees who earn more than the average
SELECT ename, salary FROM emp
WHERE  salary > (SELECT AVG(salary) FROM emp);       inner gives 47500 → Asha, Meera

2. Multiple-row subquery

Returns several values; used with IN, ANY, ALL.

-- employees working in departments located in Pune
SELECT ename FROM emp
WHERE  dept IN (SELECT dept_name FROM dept WHERE location = 'Pune');

3. Correlated subquery

The inner query refers to a column of the outer query, so it is re-evaluated once for each outer row.

-- employees who earn more than the average of their own department
SELECT e.ename, e.dept, e.salary
FROM   emp e
WHERE  e.salary > (SELECT AVG(salary) FROM emp WHERE dept = e.dept);
IT average = 55000 → Meera (60000). ENTC and HR have one employee each → none

4. EXISTS and NOT EXISTS

Test only whether the inner query returns any row. Faster than IN for big results and safe with NULLs.

-- departments that have at least one employee
SELECT d.dept_name FROM departments d
WHERE  EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);

-- departments with no employees
SELECT d.dept_name FROM departments d
WHERE  NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id);   → FINANCE

5. Subquery in FROM (inline view) and in SELECT

-- departments whose average salary is above 45000 (inline view)
SELECT dept, avg_sal
FROM   (SELECT dept, AVG(salary) avg_sal FROM emp GROUP BY dept)
WHERE  avg_sal > 45000;

-- scalar subquery in SELECT: each employee with the company average
SELECT ename, salary, (SELECT AVG(salary) FROM emp) AS company_avg FROM emp;

6. Multi-level nesting

-- employee(s) with the second-highest salary
SELECT ename, salary FROM emp
WHERE  salary = (SELECT MAX(salary) FROM emp
                  WHERE  salary < (SELECT MAX(salary) FROM emp));       → Asha (50000)

PL/SQL: Block Structure and Control Statements

PL/SQL (Procedural Language extension to SQL) is Oracle's procedural language. It combines SQL with programming features (variables, conditions, loops, exceptions) so that a whole task runs inside the database server in one call, which reduces network traffic and keeps business logic close to the data. Other systems have equivalents: T-SQL (SQL Server), PL/pgSQL (PostgreSQL).

General structure of a PL/SQL block

DECLARE                                  -- optional: variables, constants, cursors, user exceptions
  v_name    employees.first_name%TYPE;      -- same type as the column
  v_sal     NUMBER(8,2) := 0;
  c_tax     CONSTANT NUMBER := 0.10;
BEGIN                                    -- mandatory: executable statements
  SELECT first_name, salary INTO v_name, v_sal
  FROM   employees WHERE employee_id = 100;
  DBMS_OUTPUT.PUT_LINE(v_name || ' pays tax ' || v_sal * c_tax);
EXCEPTION                                -- optional: error handling
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('No such employee');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Error: ' || SQLERRM);
END;
/

  EXIT WHEN v_i > 5;
END LOOP;

-- WHILE loop: condition tested before each pass
WHILE v_i <= 5 LOOP
  DBMS_OUTPUT.PUT_LINE(v_i);  v_i := v_i + 1;
END LOOP;

-- FOR loop: counter is declared automatically, goes 1 to 5
FOR i IN 1..5 LOOP
  DBMS_OUTPUT.PUT_LINE('Row ' || i);
END LOOP;

3. Sequential (jump) control

EXIT leaves a loop, CONTINUE skips to the next iteration, GOTO label jumps to a label (rarely recommended), NULL; does nothing.

4. Exception handling

Predefined exceptions include NO_DATA_FOUND, TOO_MANY_ROWS, ZERO_DIVIDE, DUP_VAL_ON_INDEX. A user can define one: e_low_sal EXCEPTION; and raise it with RAISE e_low_sal;.

3.15

Stored Procedures and Functions

PYQ · Winter 2025 (IT) · Question bank Q7

A stored procedure or function is a named PL/SQL block that is compiled once and stored in the database, then called by name from SQL, other blocks or applications.

Procedure and function syntax

CREATE OR REPLACE PROCEDURE give_raise (p_emp_id IN NUMBER, p_pct IN NUMBER, p_new_sal OUT NUMBER) IS
BEGIN
  UPDATE employees SET salary = salary * (1 + p_pct/100) WHERE employee_id = p_emp_id;
  SELECT salary INTO p_new_sal FROM employees WHERE employee_id = p_emp_id;
  COMMIT;
END give_raise;
/
CREATE OR REPLACE FUNCTION annual_pay (p_sal NUMBER) RETURN NUMBER IS
BEGIN
  RETURN p_sal * 12;
END;
/
-- calling them
EXEC give_raise(101, 10, :new);                              -- procedure: a statement of its own
SELECT first_name, annual_pay(salary) FROM employees;       -- function: inside an expression

Parameter modes: IN (input, default), OUT (returns a value), IN OUT (both).

Procedure versus function

Return valueNot required; can give several results through OUT parametersMust return exactly one value with RETURN

Advantages of stored routines

  • Performance: compiled and cached; one call replaces many round trips.
  • Reuse and maintenance: logic is written once and shared by all applications.
  • Security: users get EXECUTE on a procedure without access to the underlying tables.
  • Integrity: business rules are applied consistently.
Question bank 7a · salary increments

Increase salary by 20% if < 10000, 10% if between 10000 and 20000, 5% if > 20000, and print the total salary afterwards. The question leaves exactly 10000 and 20000 open; the assumption here is 10% for 10000 to 20000 inclusive.

CREATE OR REPLACE PROCEDURE raise_salaries IS
  v_total NUMBER;
BEGIN
  UPDATE employees
  SET    salary = CASE
             WHEN salary < 10000                 THEN salary * 1.20
             WHEN salary BETWEEN 10000 AND 20000 THEN salary * 1.10
             ELSE                                   salary * 1.05
           END;

  SELECT SUM(salary) INTO v_total FROM employees;
  DBMS_OUTPUT.PUT_LINE('Total salary after increment: ' || v_total);
  COMMIT;
END raise_salaries;
/

Question bank 7b · total tax

No tax if salary < 5000, 10% if < 10000, 15% if < 20000, 20% above 20000. Print the total tax paid. Assumption: a salary of exactly 20000 or more is taxed at 20%, and 5000 to 9999 at 10%.

CREATE OR REPLACE PROCEDURE total_tax IS
  v_tax   NUMBER;
  v_total NUMBER := 0;
BEGIN
  FOR r IN (SELECT salary FROM employees) LOOP
    IF    r.salary < 5000  THEN v_tax := 0;
    ELSIF r.salary < 10000 THEN v_tax := r.salary * 0.10;
    ELSIF r.salary < 20000 THEN v_tax := r.salary * 0.15;
    ELSE                     v_tax := r.salary * 0.20;
    END IF;
    v_total := v_total + v_tax;
  END LOOP;
  DBMS_OUTPUT.PUT_LINE('Total tax paid: ' || v_total);
END total_tax;
/

Check by hand with salaries 4000, 8000, 15000, 25000: tax = 0 + 800 + 2250 + 5000 = 8050.

3.16

Cursors

Question bank · Q9

A cursor is a pointer to the private memory area (context area) where Oracle keeps the result of a SQL statement. A plain SELECT INTO can fetch only one row; a cursor lets a PL/SQL program process a multi-row result one row at a time.

Types

TypeCreated byUse
Implicit cursorOracle automatically for every INSERT, UPDATE, DELETE and single-row SELECT INTOCheck the outcome with SQL%ROWCOUNT, SQL%FOUND
Explicit cursorThe programmer, with a name, for a query returning many rowsRow-by-row processing

Life cycle of an explicit cursor

-- print every IT employee, with a running count
DECLARE
  CURSOR c_emp IS                                       -- 1. DECLARE
    SELECT first_name, salary FROM employees WHERE department_id = 60;
  v_name employees.first_name%TYPE;
  v_sal  employees.salary%TYPE;
BEGIN
  OPEN c_emp;                                             -- 2. OPEN: runs the query
  LOOP
    FETCH c_emp INTO v_name, v_sal;                       -- 3. FETCH one row
    EXIT WHEN c_emp%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(c_emp%ROWCOUNT || '. ' || v_name || ' ' || v_sal);
  END LOOP;
  CLOSE c_emp;                                            -- 4. CLOSE: frees memory
END;
/

-- shorter: the cursor FOR loop opens, fetches and closes automatically
FOR r IN c_emp LOOP  DBMS_OUTPUT.PUT_LINE(r.first_name);  END LOOP;

-- implicit cursor attribute after DML
UPDATE employees SET salary = salary + 100 WHERE department_id = 60;
DBMS_OUTPUT.PUT_LINE(SQL%ROWCOUNT || ' rows updated');

Cursor attributes

AttributeTrue / value when
%FOUNDThe last fetch (or DML) returned a row
%NOTFOUNDThe last fetch returned no row; used to exit the loop
%ISOPENThe cursor is open
%ROWCOUNTNumber of rows fetched (or affected) so far

A parameterised cursor takes arguments: CURSOR c(p_dept NUMBER) IS SELECT ... WHERE department_id = p_dept; and is opened with OPEN c(60). A cursor used with FOR UPDATE locks the fetched rows. In other languages the same idea is a JDBC ResultSet.

Triggers

PYQ · Winter 2025 (E&TC) · short note

A trigger is a stored PL/SQL block that the database fires automatically when a specified event (INSERT, UPDATE or DELETE on a table) occurs. Unlike a procedure it is never called by name.

Syntax

CREATE OR REPLACE TRIGGER trigger_name
  {BEFORE | AFTER | INSTEAD OF}  {INSERT | UPDATE [OF column] | DELETE}
  ON table_name
  [FOR EACH ROW]
  [WHEN (condition)]
BEGIN
  ... statements, using :OLD and :NEW ...
END;

TimingBEFORE / AFTERFire before the change (validate or modify values) or after it (audit, cascade)
EventINSERT / UPDATE / DELETEWhich operation fires it

Example 1 · enforce a business rule (BEFORE, row-level) 
CREATE OR REPLACE TRIGGER trg_check_salary
BEFORE INSERT OR UPDATE OF salary ON employees
FOR EACH ROW
BEGIN
  IF :NEW.salary < 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Salary cannot be negative');
  END IF;
END;
/
Example 2 · audit trail (AFTER, row-level) 
CREATE TABLE salary_audit (emp_id NUMBER, old_sal NUMBER, new_sal NUMBER, changed_on DATE, changed_by VARCHAR2(30));

CREATE OR REPLACE TRIGGER trg_audit_salary
AFTER UPDATE OF salary ON employees
FOR EACH ROW
WHEN (OLD.salary <> NEW.salary)
BEGIN
  INSERT INTO salary_audit
  VALUES (:OLD.employee_id, :OLD.salary, :NEW.salary, SYSDATE, USER);
END;
/
Example 3 · no double booking in the hotel schema 
CREATE OR REPLACE TRIGGER trg_no_overlap
BEFORE INSERT ON booking
FOR EACH ROW
DECLARE v_cnt NUMBER;
BEGIN
  SELECT COUNT(*) INTO v_cnt FROM booking
  WHERE  hotelNo = :NEW.hotelNo AND roomNo = :NEW.roomNo
  AND    :NEW.dateFrom < dateTo AND :NEW.dateTo > dateFrom;
  IF v_cnt > 0 THEN RAISE_APPLICATION_ERROR(-20002, 'Room already booked'); END IF;
END;
/

Oracle raises a mutating-table error (ORA-04091) when a row-level trigger reads its own table during a multi-row change; the usual fix is a compound trigger. For an exam answer the logic is what matters.

Uses and cautions

  • Uses: complex integrity rules, audit logs, automatic derived values, replication, preventing invalid transactions.
  • Cautions: hidden logic that is hard to debug, performance cost on every DML, risk of cascading triggers, and the mutating-table restriction.
  • ALTER TRIGGER t DISABLE / ENABLE; DROP TRIGGER t.

3.18

Assertions

An assertion is a condition that the database must always satisfy, defined at schema level rather than on one table. It is the standard SQL way to state rules that span several rows or tables, which a column CHECK cannot express. The DBMS tests it after every change that could violate it and rejects the change if the condition becomes false.

CREATE ASSERTION sum_check
  CHECK ( (SELECT SUM(balance) FROM account WHERE branch = 'Pune')
         <= (SELECT credit_limit FROM branch WHERE name = 'Pune') );

-- every student must have at least one enrolment
CREATE ASSERTION every_student_enrolled
  CHECK ( NOT EXISTS (SELECT * FROM student s
                   WHERE NOT EXISTS (SELECT * FROM enrolment e WHERE e.roll_no = s.roll_no)) );

DROP ASSERTION sum_check;

3.19

Roles and Privileges (Authorisation)

PYQ · Winter 2025 (IT)

Authorisation decides what an authenticated user may do. SQL controls this with privileges granted to users and roles.

Privileges

KindExamples
System privilegesCREATE TABLE, CREATE VIEW, CREATE SESSION, DROP ANY TABLE
Object privilegesSELECT, INSERT, UPDATE (column), DELETE, REFERENCES, EXECUTE on a specific object
GRANT SELECT, UPDATE (salary) ON employees TO clerk1;
GRANT SELECT ON employees TO clerk2 WITH GRANT OPTION;     -- clerk2 may pass it on
GRANT ALL ON department TO PUBLIC;
REVOKE UPDATE ON employees FROM clerk1;               -- revoking cascades to those they granted

Roles

A role is a named bundle of privileges. Grant the role to users instead of granting each privilege separately.

CREATE ROLE hr_clerk;
GRANT SELECT, INSERT ON employees TO hr_clerk;
GRANT hr_clerk TO asha, rohan;           -- both get the same rights
REVOKE hr_clerk FROM rohan;

ModelWho decides accessHowExample
DAC DiscretionaryThe owner of the objectOwner grants and revokes privileges (GRANT)SQL GRANT, Unix file permissions

RBAC suits organisations best: when someone changes job, only the role assignment changes. Views are another security tool (3.5), and stored procedures with EXECUTE rights hide tables completely.

3.20

Embedded SQL and Dynamic SQL

PYQ · Winter 2025 (E&TC) · short note

Embedded SQL

SQL statements written inside a host language such as C, C++, COBOL or Java. A precompiler replaces them with library calls before the normal compiler runs. The SQL is fixed at compile time (static SQL), so the query can be parsed and optimised in advance.

  • Every statement begins with EXEC SQL and ends with a semicolon (in C).
  • Host variables carry values between program and database. They are declared in a DECLARE SECTION and written with a colon in SQL.
  • The communication area SQLCA or SQLSTATE reports success or errors.
  • A query returning many rows uses a cursor, because the host language handles one row at a time.
/* Embedded SQL in C */
EXEC SQL BEGIN DECLARE SECTION;
  int    v_id = 101;
  char   v_name[40];
  float  v_sal;
EXEC SQL END DECLARE SECTION;

EXEC SQL CONNECT TO college;
EXEC SQL SELECT ename, salary INTO :v_name, :v_sal
         FROM   emp WHERE eid = :v_id;
if (sqlca.sqlcode == 0)  printf("%s earns %.2f\n", v_name, v_sal);

EXEC SQL DECLARE c1 CURSOR FOR SELECT ename FROM emp WHERE dept = 'IT';
EXEC SQL OPEN c1;
EXEC SQL FETCH c1 INTO :v_name;       /* repeat until sqlcode = 100 (no more rows) */
EXEC SQL CLOSE c1;
EXEC SQL COMMIT;

Dynamic SQL

SQL statements that are built as text and executed at run time, used when the table, columns or conditions are not known until the program runs (for example a search screen with optional filters).

-- PL/SQL: native dynamic SQL
DECLARE
  v_table VARCHAR2(30) := 'EMPLOYEES';
  v_count NUMBER;
BEGIN
  EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM ' || v_table INTO v_count;
  EXECUTE IMMEDIATE 'DELETE FROM employees WHERE department_id = :d' USING 50;   -- bind variable
  EXECUTE IMMEDIATE 'CREATE TABLE temp_log (msg VARCHAR2(100))';              -- DDL is possible too
END;
/

-- standard embedded form: PREPARE once, EXECUTE many times
EXEC SQL PREPARE stmt FROM :sql_text;
EXEC SQL EXECUTE stmt USING :v_dept;

-- JDBC equivalent
PreparedStatement ps = con.prepareStatement("SELECT * FROM emp WHERE dept = ?");
ps.setString(1, "IT");  ResultSet rs = ps.executeQuery();

Code: 'SELECT * FROM users WHERE name = ''' || p_name || ''''. If a user types x' OR '1'='1, the condition is always true and all rows are returned. Prevention: use bind variables (:d, ?), prepared statements, and validate inputs.
